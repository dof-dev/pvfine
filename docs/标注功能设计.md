设计一个类似标注的功能，核心目的是解决“哪个配置配什么东西”的问题：

- 标注走规则配置，而非针对具体内容的单独标注
- 标注内容包括 title/content
- 标注在编辑器内的显示：
  - 在被标注内容旁边直接加上一个 tag 显示标题，hover tag 显示 tooltip
  - 复制内容的时候不要复制标注
- 标注规则：
  - 可指定生效的文件后缀
    - 如：.equ 文件下的 [rarity]，标注为“装备品级”
    - 如果不指定后缀，则全局生效
  - 可对 section 本身进行标注
  - 可对 section 内的数据进行标注
    - 指定 section 内第几个 token（或者范围）
    - 标注类型
      - 枚举，如稀有度的 3-神器、4-史诗
      - 关联 id，可指定关联的类型，标注显示其 id 对应的 name，且可通过 cmd/ctrl + 单击跳转到对应文件
  - 可对路径，包括目录和文件进行标注，此标注显示在现有文件树的 name tag 位（一般不会对有 name 的做标注，但设计上可以共存）

- 标注规则第一版用 json 文件定义，设计好 json 结构。

## 已确认的产品约束

- 第一版规则为系统内置规则，不在应用内提供用户编辑入口。
- 规则通过单独的 HTML 可视化编辑器维护，由 Go 本地服务提供页面、校验、预览和实时写盘能力。
- 配置统一放在根目录 `config/`：`annotations.json` 保存规则，`lists.json` 保存固定的 lst/关联索引。HTML 编辑器只写入 `config/annotations.json`，写入前将旧内容保存为 `annotations.json.bak`。
- 规则和列表配置通过 `go:embed` 提供启动默认值；应用工具栏提供手动重载按钮，可在运行中校验并切换到磁盘上的最新配置。
- section 名称重复时，规则匹配全部同名 section，不配置 occurrence。
- Tag 的显示位置通过设置面板切换，设置面板在标注功能之前完成。
- 多条规则命中同一位置时，Tag 只显示规则列表中的第一条，Tooltip 显示全部命中规则。
- 引用 ID 的 Cmd/Ctrl + 单击只负责打开目标文件，不要求定位到目标 section 或 token。

## 可行性结论

整体可行性较高，但这是一个跨越 PVF 解析、规则匹配、编辑器渲染和文件跳转的功能，不是简单的文本后缀处理。

当前 PVF 脚本由固定 5 字节 token 流组成，section 和 token 类型已经明确，适合实现结构化匹配。现有反编译器只返回纯文本，没有保留 token 对应的文本范围；CodeMirror 目前也只接收纯文本文档。因此最关键的工作是建立“语义 token 到编辑器文本范围”的映射。

文件树已经有 Tag 展示能力，现有搜索索引也具备 ID、名称和路径关联的基础。路径标注可以较低成本复用这部分能力；section/token 标注和引用跳转需要新增通用的标注引擎。

## 推荐总体方案

### 1. 内置规则

建议使用以下结构：

```text
config/annotations.json
config/lists.json
internal/annotations/loader.go
tools/annotation-editor.html
```

Go 通过 `go:embed` 加载两个配置文件，应用启动时完成规则和列表配置解析、合并与校验。配置文件不写入 PVF。

HTML 编辑器负责规则列表管理、规则排序、表单编辑、JSON 导入导出、错误展示和示例预览。它不直接依赖浏览器文件系统权限，而是由 `cmd/annotation-editor` 启动仅监听 loopback 的 Go HTTP 服务，并自动打开系统浏览器。

启动命令为：

```text
task annotation:editor
```

服务监听 `127.0.0.1:0`，使用系统分配的随机端口，并为 API 请求附加当前会话令牌。提供以下接口：

- `GET /api/rules`：读取并校验当前规则，同时提供只读的列表关联供规则选择。
- `PUT /api/rules`：只校验并写入 `annotations.json`；通过后创建 `.bak`，再使用临时文件和 rename 原子替换源文件，`lists.json` 不由规则编辑器修改。
- `POST /api/preview`：使用提交的当前规则、示例路径和反编译文本调用 Go 规则引擎，返回编辑器标注和路径标注。

表单的有效修改会在短暂防抖后实时保存。校验失败时展示具体错误，且不能覆盖现有 JSON。导入和导出继续保留，便于批量维护和迁移规则。

每次有效保存还会同步运行时规则和列表配置到 `os.UserConfigDir()/pvfine/annotations.json`、`lists.json`。应用内“重载标注规则”按钮在开发环境优先读取仓库源文件，发布环境读取运行时副本。重载会先完整校验两个文件；失败时保留当前规则引擎，成功后重建路径标注、清空 relation/编辑器标注缓存、搜索索引，并刷新已打开文件和当前文件树。

规则文件中应保留 `version` 和可选的 `description` 字段，便于后续升级格式和说明规则用途。

### 2. JSON 结构

建议第一版只使用扩展名匹配、路径 glob 匹配和精确 section 名称匹配，不引入正则表达式。

```json
{
  "version": 1,
  "rules": [
    {
      "id": "equ.rarity",
      "match": {
        "extensions": [".equ"]
      },
      "target": {
        "kind": "token",
        "section": "rarity",
        "index": 0
      },
      "annotation": {
        "title": "装备品级",
        "type": "enum",
        "values": {
          "3": "神器",
          "4": "史诗"
        }
      }
    },
    {
      "id": "equ.related-equipment",
      "match": {
        "extensions": [".equ"]
      },
      "target": {
        "kind": "token",
        "section": "related",
        "index": 0
      },
      "annotation": {
        "title": "关联装备",
        "type": "reference",
        "relation": "equipment"
      }
    },
    {
      "id": "path.equipment",
      "match": {
        "glob": "equipment/**/*.equ"
      },
      "target": {
        "kind": "path"
      },
      "annotation": {
        "title": "装备配置",
        "type": "text",
        "content": "装备相关配置文件"
      }
    }
  ]
}
```

固定列表和关联索引单独放在 `config/lists.json`：

```json
{
  "version": 1,
  "relations": {
    "装备": {
      "listPath": "equipment/equipment.lst",
      "idToken": 0,
      "pathToken": 1,
      "recordTokens": 2,
      "nameSection": "name"
    }
  }
}
```

结构约定如下：

- `target.kind` 支持 `path`、`section`、`token`。
- `section` 目标匹配所有同名 section。
- token 下标使用 0-based；范围使用 `start` 和 `endExclusive`。
- token 目标可以配置 `recordTokens`，按固定数量的 token 重复匹配每条记录；`contextIndex` 可覆盖关联类型指定的上下文 token 下标。
- 默认只计算 section 的直接 token，不递归计算嵌套 section。
- `annotation.type` 支持 `text`、`enum`、`reference`。
- enum 使用 token 的规范化值作为 key。
- reference 通过 `config/lists.json` 中的 relation 类型解析目标文件、目标 ID 和 name。
- 普通 relation 使用固定 `listPath`；`kind: "contextual"` 的 relation 使用 `contextToken` 指定的同一条记录上下文值，从 `contextPaths` 选择对应的 lst，再用目标 ID 查找技能文件。例如 `[skill levelup]` 每条记录有 3 个 token，目标为 `index: 1`、`recordTokens: 3`，关联类型可把 `[fighter]` 映射到 `skill/fighterskill.lst`。
- 规则数组顺序就是优先级。

### 3. 编辑器标注模型

后端解析当前文件时，同时返回编辑器文本和标注范围：

```text
text
annotations: [
  {
    start,
    end,
    title,
    content,
    type,
    targetFileIndex
  }
]
```

`start/end` 使用 JavaScript UTF-16 code unit 偏移，避免中文和代理对字符导致 CodeMirror 定位错误。

标注不能写入编辑器文档。前端使用 CodeMirror Decoration/Widget 在 token 或 section 旁边渲染 Tag，Tooltip 使用聚合后的全部命中规则。由于 Widget 不属于 `state.doc`，复制内容时不会复制标注；复制行为仍需要通过前端测试验证。

同一文件、同一 section/token 范围的多条命中应聚合成一个 anchor：

- 可见 Tag 使用第一条规则的 title。
- Tooltip 按规则顺序显示全部 title/content。
- 引用 Tag 携带 `targetFileIndex`，Cmd/Ctrl + 单击调用现有文件打开流程。

编辑文本后只重新计算当前文件的标注，不能通过整体替换 CodeMirror 文档刷新，否则可能导致光标和选择范围跳动。

### 4. 文件树标注

路径标注需要同时支持目录和文件。当前文件树标签主要按文件索引保存，应扩展为按归档路径保存，例如：

```go
map[string][]AnnotationTag
```

`ListChildren` 返回目录或文件节点时，根据完整路径附加标注。文件原有的 name、ID 关联标签与路径标注可以同时存在。

### 5. 显示设置

Tag 的显示位置属于前端设置，不放入规则 JSON。设置面板完成后建议预留以下设置：

```text
annotation.tagPlacement:
  after-target
  line-end
  hidden
```

显示设置只影响 Tag 的渲染位置和可见性，不影响 Tooltip 中的完整标注内容。

设置通过 Wails `SettingsService` 读写，不由前端直接操作文件。设置文件位于：

```text
os.UserConfigDir()/pvfine/settings.json
```

默认值为 `after-target`，保存时同样使用临时文件和 rename 原子替换。第一版设置面板只提供标注显示位置，保留后续扩展通用设置的结构。

## 性能策略

- 路径标注在建立目录索引时计算。
- 搜索索引从 `relations` 中读取固定 `listPath` 和 contextual `contextPaths`，装备、道具、技能等列表不再在索引器内重复配置。
- section/token 标注只在打开文件或编辑当前文件时计算，不在打开归档时解析所有 `.equ` 文件。
- reference 索引按 relation 类型懒加载并缓存。
- 当前文件标注按文件索引和精确编辑器文本缓存；切换归档或修改文本时失效。
- 对不支持的 `TypeUnicode` 文件，第一版只提供路径标注；section/token 标注先限定为 `TypeScript`。
